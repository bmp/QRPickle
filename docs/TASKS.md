## Release blocker (found 2026-11-04): Cloud OTA update check fails
- [ ] **Cloud OTA can't check for updates** ("TLS: X509 - Certificate verification failed", every check: automatic at 2 min, manual, 15 s after boot). **Also v0.2.5** (its Cloud OTA screen showed no GitHub version on 2026-11-04), so devices in the field can't update over the air; they need the web console upload. Not caused by v0.2.6.
  - Chain served by bmp.github.io and bharathpalavalli.com: leaf -> Let's Encrypt YR1/YR2 -> ISRG Root YR (cross-signed by ISRG Root X1); verifies with OpenSSL on a PC. In October (v0.2.5 release) the same chain passed 6/6 on the device.
  - Diagnostic build (mbedtls_x509_crt_verify on the served chain, logs in `release/logs/2026-11-04-*`): the leaf -> YR1 link (RSA-2048) verifies every time; links checked with the 4096-bit roots (YR1 by Root YR, Root YR by X1) mostly fail with flags 0x08 ("not correctly signed by the trusted CA"); the same full verify passed in 2 of 5 runs. Heap during the handshake fell to 200-700 B in some runs ("SSL - Memory allocation failed" once), but the check also fails 15 s after boot with 2 KB left.
  - Tried and reverted (no effect): adding ISRG Root YR/YE; adding the YR1-YR3 intermediates (one 2048-bit check only).
  - Next: instrument mbedTLS (verify callback with per-certificate flags, `heap_caps` during the handshake); compare an ECDSA test host; the v0.3 port (ESP-IDF 5, mbedTLS 3, dynamic TLS buffers) as a likely fix. Until then v0.2.6 is not tagged (owner's rule: release only if it works).

- [ ] **Backups with secrets (owner 2026-10-12: passphrase or GPG):** at backup time the user picks one; without either, backups stay secret-free as now. Secrets are encrypted **on the device**, never sent in plain form.
  - **Passphrase:** AES-256-GCM, key from the passphrase with PBKDF2-SHA256 (high iteration count, random salt and nonce stored in the backup); restore asks for the passphrase and decrypts on the device.
  - **GPG:** the user uploads an OpenPGP public key (stored in LittleFS); the device encrypts the secrets to it (an OpenPGP message `gpg --decrypt` opens). Restore: decrypt on the computer with `gpg`, then restore that file (the secrets then cross the LAN once in plain form; the page says so).
  - Check first: flash cost (passphrase small with mbedTLS; OpenPGP more, at 85.5 % of the slot), PBKDF2 time on the ESP32 (a few seconds is fine), and compatibility tests against `gpg` (RSA and Curve25519 keys).
  - Not planned: revealing full secrets in the console (plain HTTP on the LAN) and board-tied keys (a MAC-derived key isn't secret; a stored key is lost on a full erase; eFuses are irreversible).
- [ ] **Improv Serial in the firmware (owner 2026-10-12):** answer the web installer, so it can set up WiFi right after flashing, show the installed version and offer "update". Check the flash cost.
